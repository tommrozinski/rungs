Task 2.1 (008 REQ-002 to REQ-010: PayoffSimulator)
---------------------------------------------------
Status: done.

Money rounding finding: `Money.times(BigDecimal)` already does exactly what REQ-002 asks
— an exact `BigDecimal` multiply (no context truncation) followed by one `setScale(0,
HALF_EVEN)` to the cent — so no new Money method was needed. The simulator computes each
debt's monthly rate factor once via `annualInterestRate.divide(BigDecimal.valueOf(1200),
MathContext.DECIMAL128)` and calls `Money.ofCents(balance).times(factor)` for interest;
`interestOfExactlyHalfACentRoundsHalfEvenDown`/`...RoundsHalfEvenUp` pin both rounding
directions (8 cents and 24 cents at a 75% rate both cross a .5-cent boundary).

Added `PayoffSimulator` (domain.projection): a stateless public final class with a
private static final `Run` inner class holding one simulation's working state as
parallel arrays indexed by supplied position (`long[]` cents for balances/minimums, one
`BigDecimal` monthly-rate-factor per debt). The payoff order is resolved once at
construction via `input.ordering().order(debts)`, mapped back to supplied indices. Each
month runs REQ-002's five steps in order (interest, minimums, pool, cascade, retire);
`MonthlyPeriod.lines()` is built in supplied order from debts unretired at the *start* of
the month, matching REQ-006. Balance/pool arithmetic uses `Math.addExact`/`subtractExact`
throughout (not plain `+`/`-`) after an early draft silently wrapped a negative-amortizing
debt's balance to a negative `long` around month ~250 of a 600-month run at rate 100%,
which then produced a negative "payment" — a real correctness bug (silent wraparound, not
loud failure) that the exact-arithmetic helpers convert into a thrown
`ArithmeticException` instead. All fields on `Run` are final (AC-E), including the
mutable arrays (only their *contents* mutate); the two per-run running totals
(`pendingFreedMinimumCents`, `totalInterestCents`) are locals inside `run()`, not fields,
for the same reason.

`monthsToDebtFreedom` (REQ-007): a debt is "payable" unless it is unretired at the
horizon with a closing balance at or above its starting balance (the given definition of
unpayable). If any payable debt is still unretired, the result is null; otherwise it is
the latest retirement month among payable debts (0 if there are none, which also covers
the no-debts case).

Added test-only `FixedOrder` (REQ-012) and `PayoffSimulatorTests` (18 tests): each
REQ-002 step in isolation (interest rounding both directions, a minimum above the
remaining balance, a two-debt cascade in one month, a freed minimum arriving the
following month, not the same one), negative surplus as $0, AC-2.3 (unpayable debt at a
600-month horizon — sized so a bounded, contaminating freed-minimum pool from a second
debt still can't out-pace the unpayable debt's growing interest, so it stays genuinely
unpayable for the full horizon), AC-2.4 (zero surplus/extra minimums-only), AC-2.5
(horizon truncation with a null `monthsToDebtFreedom`), a debt retiring exactly on the
final horizon month (not truncated — the one case needed to fully cover the
`month == horizonMonths && remaining > 0` branch), no debts, determinism, AC-2.2
(avalanche ≤ snowball on the design's three-debt scenario), single-debt schedules
identical under both strategies, a fixed-order-not-reselected case (009's success
metric), `monthRetired` against a simulated schedule, a 50-debt/600-month sanity-timing
test, and the AC-2.1 CSV fixture comparison. A shared `assertAccountingInvariant` helper
(REQ-009: total payments = total interest + starting − final balance per debt; no
negative balance) runs against every schedule built in the test class.

Golden generation: `spec/008-debt-payoff-simulation-engine/golden-payoff.py` re-implements
REQ-002 fresh from the requirements text (not translated from the Java) using Python's
`decimal` module — a `Context(prec=34, ROUND_HALF_EVEN)` for the rate ÷ 1200 division
(mirroring `MathContext.DECIMAL128`), an ambient `getcontext().prec = 60` so the
subsequent balance × factor multiply is effectively exact (not re-rounded by a low
default context precision), and a single explicit `.quantize(Decimal("0.01"),
ROUND_HALF_EVEN)` for the one monetary rounding. Run once
(`python3 spec/008-debt-payoff-simulation-engine/golden-payoff.py`) to write
`src/test/resources/golden/payoff-three-debts-snowball.csv` (35 rows: all three debts
retire by month 20 given a $300 surplus). No Java/Python disagreement: the Java
`PayoffSimulatorTests.ac21ThreeDebtSnowballScheduleMatchesTheIndependentlyComputedGoldenCsv`
test compares every row (month, debtId, opening/interest/payment/closing balance,
retired) and passes on the first run — the two implementations, written independently
from the same requirements text, agree to the cent.

AC-2.1 headline numbers (design.md §3 scenario: surplus $300, extra $0, horizon 360):
snowball 20 months to debt freedom, $1,066.76 total interest; avalanche 20 months,
$930.20 total interest (avalanche ≤ snowball, confirming AC-2.2 on this scenario;
verified identical between the Java simulator and the Python golden script).
