2. New package `domain.projection`: PayoffScheduleCalculator
   - Records: ScheduleLoan(name, startingBalance, annualRate, minimumPayment), LoanMonth(open, interest,
     payment, end), ScheduleMonth(month, extraCash, cascade, totalAvailable, loanMonths, monthInterest,
     totalBalance, cumulativeInterest), PayoffSchedule(loans, months, totalExtraCash, totalPaidPerLoan,
     totalInterest, truncated).
   - PayoffScheduleCalculator.schedule(FinancialSnapshot): debts sorted by rate descending (stable sort keeps
     supplied order on ties), mortgage appended last only when its balance is above $0 (name "Mortgage",
     minimum = its monthly payment). extraCash = max(monthlySurplus, $0), constant every month. Each month:
     cascade = sum of minimums of loans closed by an earlier month (freed minimum counted once, the month
     after it closes, not the closing month itself); totalAvailable = extraCash + cascade; for each open loan
     in order, interest = open * rate/1200 (DECIMAL128 monthly rate, Money.times half-even cents, same
     pattern as MortgagePayoffCalculator), payment = min(open+interest, minimum+pool), pool reduced by
     max(payment-minimum, 0) after each loan; end = open+interest-payment (always >= 0 since payment is
     capped at open+interest). Closed loans render as an all-$0 LoanMonth. Stops the month the last loan's
     balance reaches $0, or at 600 months (`truncated=true`); any ArithmeticException (overflow) part-way
     through a month is caught and also treated as truncated, per the task's "must not throw" requirement,
     rather than propagating.
   - No loans (renter with no debts, or a paid-off mortgage and no debts) returns an empty schedule with all
     totals at $0 and `truncated=false`, without entering the simulation loop.

## Review fixes

Six review findings, fixed with TDD (one failing test per behavior, then the minimal fix), on top of the
uncommitted phase-3 web work above.

1. **Unbounded schedule size (medium).** A debt-row cap of 20 now runs end to end: `SnapshotController`'s
   `@InitBinder` sets `setAutoGrowCollectionLimit(20)` (was 100) so `debts[20]` and up hit
   `handleUnreachableDebtIndex()` as a 400, the same path `debts[99999]` already used; `addDebt` (`POST
   /debts/add`) silently no-ops once the form already holds 20 rows instead of adding a 21st; and
   `SnapshotFormMapper.toSnapshot` keeps only the first `MAX_DEBT_ROWS` (20) non-zero-balance rows in
   submitted order, documented on the constant and the class javadoc, dropping any further rows rather than
   mapping them.
   - Note on the binder limit: the task described this as "autoGrowCollectionLimit 21 (index 20 → 400)"; a
     small experiment against `BeanWrapperImpl` directly (Spring 7.0.9) showed the limit itself is the
     rejection threshold — `index >= limit` throws `InvalidPropertyException` — so a limit of 20 (not 21) is
     what actually produces "debts[19] is the 20th and last row, debts[20] is a 400", the exact observable
     behavior the task asked for. Implemented with 20.
   - New tests: `SnapshotFormMapperTests.onlyTheFirstTwentyNonZeroDebtRowsAreKept` (25 rows in, 20 kept, in
     order); `SnapshotControllerTests.addDebtAtTwentyRowsDoesNotAddAFurtherRow` (posts 20 rows, `POST
     /debts/add`, asserts `debts[19].label` present and `debts[20].label` absent).
   - `PayoffScheduleControllerTests.twentyDebtsAtTheSixHundredMonthCapStayWellUnderTheOldFiftyDebtSize`: 20
     debts, each with a minimum a little below its own monthly interest (same shape as the calculator's own
     600-cap test), so all 20 stay open for the full 600-month cap — the largest a breakdown page can be, and
     the same shape as the pre-fix bug (50 debts × 600 months, 6.6 MB). Measures the `POST /breakdown` response
     byte size. Measured ~2.0 MB at 20 debts, well under both the old 6.6 MB and a straight 50-to-20 scaling of
     it (~2.64 MB); asserts under 2.2 MB. The task's own "~1.5 MB" figure wasn't reachable purely by capping
     row count — at 20 loans × 600 months the table is ~52,000 `<td>`s, and the template's own per-cell
     indentation/whitespace (not the debt count) is the remaining ~38 bytes/cell; trimming that is a template
     change outside this task's blast radius (binder + mapper + controller row cap only), so it's flagged here
     rather than done silently.

2. **Freed-minimum leak in `PayoffScheduleCalculator` (low).** Fixed the exact bug: when an open loan's payoff
   amount lands below its own minimum (e.g. its last small payment), the unused part of that minimum was
   discarded instead of flowing to the next loan the same month. Replaced the old `overMinimum =
   max(pmt − minimum, 0); pool -= overMinimum` (loses the case where pmt < minimum) with `pool = pool +
   minimum − pmt` — algebraically identical when pmt ≥ minimum, but now also correct when pmt < minimum: pool
   *increases* by the unused part. Never negative, since pmt = min(open + int, minimum + pool) can never
   exceed minimum + pool. design.md 040 §3 step 4 rewritten to state this rule directly (pool = pool + minimum
   − pmt) instead of the old one-sided "reduces it by (pmt − minimum) when that difference is positive"
   wording, which was the buggy rule spelled out.
   - The existing hand-verified two-debt test (first three months) doesn't change: rechecked by hand — every
     loan's payment that month is always ≥ its minimum in that fixture (owed always exceeds minimum before
     either loan closes), so the old and new pool formulas agree there and no figure moved.
   - New test: `aLoanClosingBelowItsMinimumFreesTheLeftoverToTheNextLoanInTheSameMonth` — Loan A ($10 balance,
     0%, $50 minimum) pays off at $10.00 (below its $50 minimum) and Loan B ($200 balance, 0%, $30 minimum,
     $0 extra cash) receives the $40 leftover the same month, paying $70.00 instead of just its own $30
     minimum. Failed against the old code (asserted $30.00) before the fix, passes after.

3. **Overflow → truncated (low).** New test
