## Review fixes (post-implementation code review)

- **CRITICAL — form binding 500.** `SnapshotFormController` (`POST /`, `/snapshot/debts/add`,
  `/snapshot/debts/remove/{index}`) and `AssessmentPageController` (`POST /assessment`) bind `@ModelAttribute
  SnapshotInput` by record constructor; a posted `debts[N]` at or beyond Spring's `autoGrowCollectionLimit` (256),
  e.g. `debts[99999].balance=100`, made `DataBinder.createList` throw an uncaught `IndexOutOfBoundsException`
  before either controller or `SnapshotValidator` ran, reaching the client as an HTTP 500. Separately, a sparse
  post within the limit (e.g. only `debts[200].balance` set, so the bound list has 201 entries and every one below
  200 is `null`) made `SnapshotInput.forForm()` throw an uncaught `NullPointerException` in the same request.
  Fixed with two changes, both scoped to just those two controllers:
  - Added `SnapshotBindingAdvice`, a `@ControllerAdvice(assignableTypes = {SnapshotFormController.class,
    AssessmentPageController.class})` that answers `IndexOutOfBoundsException` (the out-of-range binder failure)
    and `IllegalArgumentException` (see the field-name finding below) with a plain 400 body, no figures from the
    request and no stack trace.
  - Added `SnapshotFormController.sanitized(SnapshotInput)`: when a debt list has a `null` entry, returns a copy
    with a blank row standing in for each one, so rendering never NPEs; `SnapshotValidator.validate` still runs on
    the *original*, unsanitized submission first, so a sparse index is still correctly reported as `INVALID_TYPE`
    at that index, exactly as the API path already does. Called before `forForm()` in `changeNumbers`,
    `AssessmentPageController.assess`'s failure path, `addDebt`, and `removeDebt`.
  - Tests: `SnapshotFormControllerTests` and `AssessmentPageControllerTests` gained parameterized cases for
    `debts[256]`/`debts[99999]` (asserts 400) and a dedicated sparse-index case, `debts[200]` (asserts status <
    500), on all four endpoints.

- **MEDIUM — `text-field.html` always wired to `/snapshot/field`.** The fragment carried `hx-post="/snapshot/field"`
  unconditionally, so `/dev/components` gallery fields (names like `income`, `incomeFocus`, which are not real
  snapshot fields) posted there on blur and `FormFields.forBlur`/`topLevelField` threw an uncaught
  `IllegalArgumentException` → 500. Fixed both sides:
  - The fragment gained a `blurValidated` parameter; the `hx-*` attributes are now emitted only when it is true
    (`th:attr` with a ternary per attribute, matching the existing `th:aria-invalid`/`th:aria-describedby` idiom).
    Every real call in `snapshot/form.html` and `snapshot/field.html` now passes `blurValidated=true`;
    `dev/components.html`'s four gallery calls pass `blurValidated=false` (Thymeleaf's fragment-selection syntax
    requires every declared parameter be given a value at the call site, even if null/false).
  - `SnapshotBindingAdvice`'s `IllegalArgumentException` handler (see above) turns an unknown field name posted to
    `/snapshot/field` into a 400 instead of a 500.
  - Tests: `TextFieldFragmentTests` gained `hasNoOnBlurWiringByDefaultAsInTheComponentGallery` and
    `addsOnBlurWiringWhenRequestedAsInTheSnapshotForm`; `ComponentGalleryTests` gained an assertion that no
    gallery `input.input` carries `hx-post`; `SnapshotFormControllerTests` gained
    `onBlurWithAnUnknownFieldNameIs400`.
